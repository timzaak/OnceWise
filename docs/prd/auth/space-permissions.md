# 空间权限与角色（space-permissions）产品需求文档 (PRD)

**创建时间**: 2026-10-14
**优先级**: P0
**发布时间**: 2026-10-15

> 本 PRD 是 [`docs/prd/core/data-sync.md`](../core/data-sync.md) 的空间级权限扩展，叠加在 [`docs/prd/auth/herald-support.md`](herald-support.md) 的服务级门禁之上：行使 data-sync「无账号空间模型」决策的重开条件（出现不可信圈子的访问控制需求——按人收回权限），为 Herald 鉴权模式下新建的空间引入**角色分级、一次性邀请码与成员管理**。成员与角色事实整体托管在 Herald 组织授权能力面（组织 / 成员 / 判定 / 审计），oncewise-ai-sync 服务端仍不建账号、成员或用户资料表——「无账号」的空间模型姿态在服务端一侧保持，仅新增空间与组织的关联。
> 与 herald-support §2.2 既有排除项（"不引入空间级所有权、成员管理、角色分级、邀请"）的覆盖关系：以用户 2026-10-14 确认的立项意图为准（本 feature 立项决策，见 §8）；herald-support 与 data-sync 正式 PRD 的对应边界表述已随本 PRD 发布同步修订（限定为密钥空间与无鉴权模式口径）。
> 与原两级角色决策（DEC-data-sync-003，已被无账号模型取代）的关系：本 feature 不是恢复旧模型（旧模型两级均读写、服务端自持成员表），而是以 Herald 托管组织层重建——成员只读、成员事实不出 Herald。
> 术语：**组织绑定空间** = Herald 鉴权模式下新建、凭"登录身份 + 成员资格 + 角色"访问的空间（无空间码）；**存量密钥空间** = 升级前已存在、保持"空间ID#密钥"寻址与对等读写语义的空间；**所有者 / 管理员 / 只读成员** = 组织绑定空间的三档角色（映射 Herald 内置组织档位 org-owner / org-admin / org-member）；**邀请码** = 管理员签发的单次加入凭证；**组织** = Herald 托管的成员与角色实体，与应用侧空间一一对应。

## 1. 相关用户故事

> 详细故事与验收标准见 [`docs/user-stories/auth/space-permissions.md`](../../user-stories/auth/space-permissions.md)；角色定义（空间参与者、部署者）见 [`docs/user-stories/_roles.md`](../../user-stories/_roles.md)，本 feature 内空间参与者按能力分级为所有者 / 管理员 / 只读成员（分级已并入该文件）。

### 1.1 相关故事
- `[US-WP-001]` 创建受保护空间并成为所有者，优先级 P0，来源 `docs/user-stories/auth/space-permissions.md`
- 角色：空间参与者（创建者）
- 摘要：Herald 鉴权模式下新建空间自动受组织权限保护，创建者成为所有者；空间无空间码，加入凭邀请码

- `[US-WP-002]` 签发一次性邀请码，优先级 P0，来源同上
- 角色：空间管理员
- 摘要：签发可复制分享的单次邀请码，明示单次与有效期规则；已用码与过期码均不能再次使用

- `[US-WP-003]` 凭邀请码加入空间，优先级 P0，来源同上
- 角色：空间参与者（加入者）
- 摘要：粘贴有效邀请码即加入为只读成员；码无效/已用/过期拒绝且本机不记录；未登录先引导登录、码不被消费

- `[US-WP-004]` 只读成员使用同步，优先级 P0，来源同上
- 角色：空间参与者（只读成员）
- 摘要：浏览与拉取语义与既有空间参与者完全一致；写与管理操作被拒并明确只读原因，本机数据不受影响

- `[US-WP-005]` 管理员读写与成员管理，优先级 P0，来源同上
- 角色：空间管理员
- 摘要：读写语义照常；成员列表、提升/降级、移除（近即时生效）、最后管理员保护与成员自主退出

- `[US-WP-006]` 所有权转移，优先级 P1，来源同上
- 角色：空间所有者
- 摘要：所有权一步原子转移（原所有者降为管理员）；非所有者不能转移

- `[US-WP-007]` 存量空间与无鉴权部署零变化，优先级 P0，来源同上
- 角色：空间参与者
- 摘要：存量密钥空间与 `AUTH_MODE=none` 部署的行为与升级前逐字一致，不出现任何权限/成员/邀请界面

- `[US-WP-008]` 部署组织接入配置，优先级 P0，来源同上
- 角色：部署者
- 摘要：Herald 鉴权模式必需组织接入配置，缺配置 fail-fast 且报错含 Herald 控制台准备步骤；升级路径在发布说明完整

- `[US-WP-009]` 权限依赖异常可见，优先级 P1，来源同上
- 角色：空间参与者
- 摘要：权限依赖不可用时明确失败、可重试、不放行；结果不确定的操作先核对再重试；本地优先不回退

既有能力引用（不重复建故事）：读语义沿用 US-DS-004/006（浏览、拉取、校验、默认未启用、本地固定、状态可见），写语义沿用 US-DS-003（保存脚本、发布版本、名称/备注维护），登录与凭证生命周期沿用 US-HS-001/002（本 feature 只在其上叠加空间级角色判定）；空间生命周期（忘记/删除）沿用 US-DS-005，其中"删除"在组织绑定空间收敛为管理员能力。

## 2. 范围界定

### 2.1 包含功能
- **组织绑定空间**：Herald 鉴权模式下新建的空间一律绑定一个 Herald 组织并受角色权限保护；创建者为所有者；该类空间不再有空间码，成员凭"登录身份 + 成员资格 + 角色"访问
- **角色与能力分级**：只读成员（浏览/拉取全部读语义）；管理员（读 + 写 + 成员管理 + 邀请码签发 + 删除空间）；所有者（管理员全部能力 + 不可移除/降级 + 唯一可转移所有权）
- **一次性邀请码**：管理员签发、单次原子消费、带有效期、同空间可并存多枚、固定授予只读成员档；成员不持有空间密钥
- **成员管理**：成员列表（身份标识与角色）、提升/降级、移除（近即时生效）、成员自主退出、所有权转移；所有者与最后管理员档保护由 Herald 组织层原生保证
- **成员事实托管**：成员、角色与组织判定的唯一权威源是 Herald 组织层；服务端仅保存空间与组织的关联标识及邀请码凭据（哈希形态），不建成员/角色/用户资料表；成员列表经代理实时获取
- **部署接入**：Herald 鉴权模式必需配置组织接入凭证（绑定客户端应用的 API key，获组织管理策略授予）；缺配置启动失败并给出控制台操作指引（fail-fast）
- **异常与状态反馈**：权限判定依赖不可用时明确失败、可重试、不放行（fail-closed，沿用 US-HS-004 架构姿态）；无权访问与只读越权的原因对用户可见
- **存量与无鉴权零变化**：存量密钥空间与 `AUTH_MODE=none` 部署的行为、界面与接口语义与升级前一致（回归性要求）

### 2.2 不包含功能 (Out of Scope)
- 无鉴权模式（`AUTH_MODE=none`）的任何行为变更，包括"只读共享密钥"等无身份源的能力密钥类权限方案（逃生通道语义冻结；真实需求出现时按重开条件重评）
- 可配置角色能力（Herald 组织档位词表驱动的按部署自定义分级，如"可编辑"档）；本 feature 档位能力固定映射，不提供配置面
- 按脚本、按版本的细粒度授权（对象级 ACL）；权限只到空间级
- 按邮箱添加成员、邀请审批流、邀请邮件品牌与落地页（邀请码经现有渠道分享已覆盖加入路径；Herald 侧不提供邮箱到账号的解析能力面）
- 存量密钥空间迁移为组织绑定空间（存量空间无历史身份可定所有者，不提供自动或人工迁移工具）
- 面向空间参与者的审计或操作日志界面（Herald 侧对组织与成员操作自带审计记录，oncewise 不另建审计能力）
- 服务端持久化用户身份资料或成员关系副本（成员事实仅在 Herald；oncewise 侧仅存组织关联标识）
- 扩展直连 Herald 或内置 Herald 地址（一切经所连服务器代理，沿用 herald-support 原则）
- 移动端与非 Chrome 浏览器（沿用既有排除）
- data-sync 既有脚本、版本语义的任何变更（读/写操作的行为语义不变，仅准入判定不同）

### 2.3 依赖项
- Herald 组织授权能力面：组织创建/删除（幂等）、成员增删改查、组织级判定、按用户列组织；以绑定客户端应用的 API key 认证，读操作与写操作分别要求组织查看与组织管理策略——部署侧控制台动作，交付物为文档化准备步骤
- herald-support 已发布门禁基线：登录门禁（服务级身份校验）在前，空间权限（组织判定）叠加其后，存量密钥空间再叠加密钥校验——三层正交
- data-sync 已发布语义基线：脚本、版本、本地优先、状态反馈的全部行为语义
- 扩展同步区交互入口与既有确认/复制/i18n 交互模式
- Herald 部署 realm 内的账号体系（空间成员必须为部署 realm 内账号；跨 realm 账号不能加入）

## 3. 需求概述

### 3.1 功能描述
data-sync 的空间密钥解决"空间内谁能对等读写"，herald-support 把"进服务器的门"提前到用户身份；但空间暴露给半可信圈子（外部协作者、人员流动的团队）时，仍缺少"空间内谁能读、谁能写、谁能拉人、谁能收回"的按人控制：任何人拿到空间码即永久对等读写，泄露无法挽回。space-permissions 在 Herald 鉴权模式下把新建空间升级为组织绑定空间：创建者成为所有者，经一次性邀请码按人拉入成员；成员只读使用、管理员读写维护、所有者掌握最终控制权；人员变动时移除即收回，近即时生效。成员与角色事实不落在 oncewise 服务端——全部托管于 Herald 组织层，服务端只保存空间与组织的关联，延续"空间模型无账号"的服务端姿态。存量密钥空间与无鉴权部署完全不受影响。

### 3.2 关键特性
- **按人授权与收回**：访问权绑定"人 + 角色"而非"持有密钥"；移除成员近即时生效，旧凭证（邀请码、本机清单）不能重入
- **最小侵入托管**：成员/角色/判定/审计复用 Herald 组织层；oncewise 服务端无账号表、成员表与用户资料，升级不改变其数据面姿态
- **一次性邀请码**：单次原子消费 + 有效期，把"分享加入凭证"的泄露面压到单人单次；管理员可随时签发新码
- **读写分级**：只读成员完整保留既有读语义（浏览/拉取/本地固定），写与维护集中在管理员档——分发型团队（少数人维护、多数人使用）的默认形态
- **存量与逃生通道零变化**：既有密钥空间、无鉴权模式逐字保持升级前行为；不存在隐式三态
- **fail-closed 延续**：权限依赖不可用时拒绝服务、不放行（与门禁层同一架构取舍）
- **本地优先不回退**：被移除、降级或退出只影响服务端通道；本机流程、已拉取内容与清单条目保留

## 4. 业务规则与状态

### 4.1 业务规则
- **空间类别规则**：空间分两类，类别由服务端记录、不由用户选择——**存量密钥空间**（升级前已存在；永远保持"空间ID#密钥"寻址与持码对等读写，不绑定组织、不出现成员/邀请界面）与**组织绑定空间**（Herald 鉴权模式下新建；一律绑定组织并受角色权限保护）。无鉴权模式下新建的空间均为密钥空间
- **角色能力矩阵**：
  | 能力 | 只读成员 | 管理员 | 所有者 |
  |---|---|---|---|
  | 浏览脚本/版本/摘要、拉取版本（US-DS-004 读语义） | ✓ | ✓ | ✓ |
  | 保存脚本、发布版本、改名称/备注（US-DS-003 写语义） | — | ✓ | ✓ |
  | 签发邀请码、成员列表/提升/降级/移除 | — | ✓ | ✓ |
  | 删除空间（级联，US-DS-005 语义） | — | ✓ | ✓ |
  | 转移所有权 | — | — | ✓ |
  | 被移除/被降级 | 可 | 可（受最后管理员保护） | 不可 |
- **角色映射规则**：三档角色一一映射 Herald 内置组织档位（org-owner / org-admin / org-member）；所有者与最后管理员档保护、所有权转移原子性（原所有者降为管理员）由 Herald 组织层原生保证，oncewise 不自建保护逻辑
- **加入规则**：加入组织绑定空间的唯一途径是一次性邀请码——管理员签发（单次消费、有效期 24 小时、同空间可并存多枚、固定授予只读成员档，管理员档由提升产生）；未持有效码的登录用户不能自行加入；码的消费为单次原子动作，因服务端依赖故障失败时按既有"操作结果不确定"口径处理（先核对再重试）
- **成员资格规则**：成员必须为部署 realm 内的 Herald 账号（跨 realm 不能加入）；成员账号停用由门禁层在下一次访问拒绝（US-HS-004 语义沿用）；成员与角色的变更近即时反映到下一次访问判定
- **移除与保护规则**：所有者不可被移除或降级；任何成员变更不得使空间失去全部管理员档成员（违反即拒绝并提示先转移管理权）；移除生效后，被移除者对该空间的任何访问被拒，其本机数据与清单条目保留（可自行"忘记"），其持有的任何旧邀请码不能使其重入
- **删除级联规则**：删除组织绑定空间为管理员能力；删除时空间、组织及其全部成员关系、未使用邀请码随之失效，不产生"空间已删而组织/成员残留"的长期状态；权限依赖不可用时删除失败可重试（fail-closed）
- **访问判定顺序**：登录门禁（服务级身份校验）→ 空间权限（成员资格 + 角色判定，组织绑定空间不再要求空间密钥）→（存量密钥空间）密钥校验；三层正交，任一层拒绝即整体拒绝
- **错误区分规则**："未登录"、"无权访问（非成员）"、"角色不足（只读越权或非管理员操作）"与既有"空间密钥错误"类别相互区分，供扩展分流引导
- **身份与隐私边界**：oncewise 服务端不保存用户身份资料、不建成员表；成员列表与身份标识（Herald 侧昵称/邮箱）经代理实时获取，不落库、不进入日志

### 4.2 关键状态与异常
- 空间类别状态：存量密钥空间 / 组织绑定空间（新建即定，不可互转）
- 我的空间角色状态：所有者 / 管理员 / 只读成员 /（被移除后）无访问权
- 邀请码状态：有效 / 已使用 / 已过期（签发界面可再签新码）
- 成员状态：在册（三档角色）/ 已移除；成员账号停用视为不可访问
- 异常与兜底：
  - 邀请码无效、已用、过期 → 拒绝并区分原因，本机不记录该空间
  - 未登录时使用邀请码 → 引导登录，码不被消费，登录后原码可用
  - 只读成员执行写/管理操作 → 拒绝并明确"需要管理员权限"，本机数据不受影响
  - 非成员或被移除者访问组织绑定空间 → 拒绝并明确"无该空间访问权"；本机数据保留
  - 使空间失去全部管理员档的变更 → 拒绝并提示先转移管理权
  - 创建空间时权限依赖不可用 → 失败可重试，不产生半成品空间
  - 成员管理/加入操作结果不确定（超时）→ 先刷新成员列表核对，再决定重试
  - 权限依赖（Herald）不可用 → 拒绝、明确提示、可重试、不放行；本地流程照常
  - 存量密钥空间在升级后的一切既有异常路径 → 与升级前一致（零变化）

## 5. 功能需求

### 5.1 核心需求
- **FR1 组织绑定空间创建**：Herald 鉴权模式下创建空间即为组织绑定空间，创建者成为所有者；创建原子完成（权限登记失败即整体失败，不产生半成品）；该类空间无空间码
- **FR2 邀请码生命周期**：管理员可签发邀请码（界面展示 + 复制反馈 + 单次/有效期规则明示）；单次原子消费、24 小时有效、可并存多枚；已用/过期码使用被拒并区分原因
- **FR3 凭码加入**：粘贴邀请码加入为只读成员，空间与我的角色记入本机清单；码无效/已用/过期拒绝且本机不记录；未登录先引导登录且码不被消费
- **FR4 角色化同步使用**：读操作（浏览/拉取/状态）语义与既有完全一致；写操作与管理操作按角色矩阵放行或拒绝，拒绝原因明确到"只读成员"或"需要管理员权限"
- **FR5 成员管理**：成员列表（身份标识 + 角色 + 所有者标记，代理实时获取）、提升/降级、移除（近即时生效）、成员自主退出、所有权转移（原子，原所有者降为管理员）；所有者与最后管理员保护拒绝并给出转移指引
- **FR6 空间删除收敛**：组织绑定空间的"删除"为管理员能力，删除后组织、成员关系与邀请码随之失效；本机"忘记"语义对所有角色不变
- **FR7 部署配置**：Herald 鉴权模式必需组织接入凭证，缺配置启动失败并输出 Herald 控制台准备步骤（创建客户端应用、签发绑定应用的 API key、授予组织管理策略）；发布说明含升级迁移章节
- **FR8 零变化回归**：存量密钥空间与无鉴权部署的行为、界面与错误语义与升级前一致；新权限能力在这两类场景完全不出现
- **FR9 状态与异常反馈**：无权访问、角色不足、权限服务不可用、操作结果不确定等状态在同步区可见、原因明确、可重试；本地流程与进行中运行不受影响

### 5.2 验收目标
1. **受保护空间协作闭环**：所有者建空间 → 签发邀请码 → 同事凭码加入为只读成员 → 只读成员浏览/拉取照常、写操作被拒并明确原因 → 所有者提升其为管理员 → 其保存脚本、发布新版本成功，其他只读成员看到新版本提示——全程既有读/写/本地固定语义不变
2. **收回闭环**：管理员移除成员后，该成员下一次任何访问被拒（明确无访问权），本机数据与清单保留、可自行忘记；其持有的任何旧邀请码不能使其重入
3. **保护与转移闭环**：所有者不可被移除/降级；使空间失去全部管理员档的变更被拒并提示转移路径；所有权转移一步完成且原所有者降为管理员
4. **邀请码一次性闭环**：同一码第二次使用被拒；过期码被拒；并存多枚有效码各自可用；未登录使用不消费码
5. **零变化回归**：存量密钥空间的全部既有场景（凭码加入、对等读写、忘记/删除）原样通过；无鉴权部署不出现任何权限/成员/邀请界面，行为与升级前一致
6. **部署可预期**：缺组织接入配置的 Herald 鉴权部署启动失败，报错信息可独立指导部署者完成 Herald 控制台配置；升级路径在发布说明完整
7. **成员事实单一权威源**：成员与角色的全部变更（加入/提升/降级/移除/转移）以 Herald 组织层为唯一事实源实时一致；服务端重启或升级不改变任何成员关系，且服务端无可查询的成员/用户资料存储

## 6. API 相关约束

**适用性**: 适用（能力边界、访问控制与集成原则）

- **接口能力范围**：服务端在既有能力之外新增——组织绑定空间创建、邀请码签发与核销加入、成员列表/角色变更/移除/退出的代理能力、我的空间角色信息；成员资格与角色判定经 Herald 组织层完成，服务端不自建判定词表或成员存储。具体端点与数据契约由技术设计文档承载，不在本 PRD 展开
- **访问控制原则**：登录门禁在前（Bearer 凭证）；组织绑定空间凭"成员资格 + 角色"判定访问，不再要求空间密钥；存量密钥空间沿用 `X-Space-Key` 校验。"未登录""无权访问""角色不足"与既有空间密钥类错误以不同错误类别区分，供扩展分流引导
- **集成边界**：组织、成员、档位与判定语义以 Herald 为准（内置三档映射本 feature 三类角色；所有者/最后管理员保护、转移原子性、审计由 Herald 原生提供）；组织接入凭证（绑定客户端应用的 API key + 组织管理策略授予）为 Herald 鉴权模式必需配置，fail-fast；组织的创建与删除由 oncewise 服务端随空间生命周期驱动，与应用侧空间一一对应（幂等创建）
- **realm 边界**：空间成员必须为部署 realm 内账号，跨 realm 不能加入（Herald 组织层约束，oncewise 侧同口径透出）
- **兼容性原则**：无鉴权模式接口行为冻结；存量密钥空间契约不变；接口路径不带版本号（沿用既有承诺）；扩展不直连 Herald，一切经所连服务器代理

## 7. 前端/交互约束

**适用性**: 适用

- **页面入口**：扩展侧边栏「同步」页签——组织绑定空间的空间行显示"我的角色"标识与「成员」入口；成员界面承载成员列表、邀请码签发/复制、提升/降级、移除、退出与所有权转移；凭邀请码加入复用既有"粘贴加入"表单入口
- **关键交互**：邀请码展示沿用"只读输入 + 复制按钮 + 复制成功反馈"模式，并明示单次与有效期规则；移除成员、降级、所有权转移、删除空间为显式确认操作（沿用原生确认对话与差异化文案）；成员角色调整即时反映在成员列表
- **状态反馈**：无权访问、只读越权、权限服务不可用、操作结果不确定等状态与原因在同步区可见、可重试；被移除/降级后下一次操作的拒绝原因明确；本地流程与进行中运行不受影响
- **数据可见性**：成员列表展示 Herald 侧身份标识（昵称/邮箱），代理实时获取不落本机缓存为长期事实；本机空间清单为组织绑定空间记录"我的角色"（不记录密钥）；访问凭证安全语义沿用 herald-support（仅存本机扩展存储、不出现在 URL/日志）
- **权限可见性**：只读成员不出现写与管理入口（或入口操作后明确拒绝引导），管理员/所有者的管理入口按角色呈现；无鉴权服务器与存量密钥空间不出现任何新界面
- **国际化**：扩展 UI 以英语为主语言（en 默认 catalog），内置 zh 完整翻译；成员/邀请/角色文案同受 i18n 覆盖
- **兼容性**：沿用 Chrome 114+ 基线；不新增 manifest 权限
